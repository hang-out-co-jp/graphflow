# GraphFlow 業務フロー設計盤

業務フローをGUIで設計して、Claude Code の **dynamic workflow** スクリプトを書き出します。

お絵かきツールではありません。**契約・検証者・アンカー・人間ゲート・上限が揃うまで、書き出しをブロックします。**

```
 1段目 [同時に 5 本]   2段目        3段目        4段目        5段目
┌──────────┐      ┌────────┐   ┌────────┐   ┌────────┐   ╔════════╗
│ 並列     │      │ 整理   │   │ 検証   │   │ 統合   │   ║ 人間   ║
│ 材料を   │─────▶│ 出典の │──▶│ 事実を │──▶│ 本文を │──▶║ ゲート ║
│ 集める   │      │ ない主 │   │ 確認   │   │ 書く   │   ║ 公開可 ║
│ ×5       │      │ 張を落 │   │        │   │        │   ║ か決める║
└──────────┘      └────────┘   └────────┘   └────────┘   ╚════════╝
   線＝依存。線が入っていない仕事は、最初から同時に走る。

表題欄 │ 点検 済 │ アンカー 2件 │ 上限 7/14 │ 図面 1枚 │  [ 書き出す ]
```

## なぜGUIなのか

テキストで `ultracode:` と書けば、Claude はワークフローを書いてくれます。
それでもGUIを作った理由は3つだけです。

1. **業務フローの持ち主が、本人で読める・直せる。** JavaScript を読めない人がレビューできます。
2. **注意事項を、機械が強制する。** 契約なし・検証者が作業者と同文脈・アンカー未宣言・上限未設定は、
   文章のプロンプトだと黙って抜け落ちます。設計盤は**抜けたまま書き出させません**。
3. **図面が真実源になる。** スクリプトは生成物です。`.graphflow.json` を直して書き出しし直します。

## 使う

### インストール不要（誰でも）

**<https://claude.ai/code/artifact/fdc15677-bb31-49a5-bbbf-c936317f6835>**

ブラウザで開くだけです。書き出したスクリプトを `.claude/workflows/` に置けば動きます。

### プラグインとして（Claude Code から）

```
/plugin marketplace add hang-out-co-jp/graphflow
/plugin install graphflow@hangout
```

⚠️ **入れたら一度セッションを開き直してください。** 同じセッションのままだと、
ファイルを書けない担当（後述）がまだ見えず、書ける状態のまま走ります。

インストール後、**Claude に頼む**なら:

```
/graphflow:graphflow
```

**自分のターミナルから直接**打ちたいときは、一度だけリンクを張ります。
プラグインの `bin/` が PATH に載るのは Claude Code の Bash ツールの中だけで、
ふだんのシェルには載らないためです。

```bash
mkdir -p ~/bin        # すでに PATH に入っていることを確認してください
ln -sf <このリポジトリ>/plugins/graphflow/bin/graphflow        ~/bin/graphflow
ln -sf <このリポジトリ>/plugins/graphflow/bin/graphflow-dryrun ~/bin/graphflow-dryrun
```

以後はどこからでも:

```bash
cd ~/myproject                # ここの .claude/workflows/ に保存されます
graphflow                     # 空の図面
graphflow foo.graphflow.json  # 既存の図面を開く
```

GUI の「`.claude/workflows/` に保存」を押すと、`graphflow` を起動したディレクトリ配下に
スクリプトと図面が書き込まれます。次のセッションから `/<図面名>` で起動できます。

同梱のワークフローもすぐ使えます:

```
/graphflow:graphflow-diamond  調べたいテーマ
```

## 7つの部品

記事「AIを1人の天才から100人の組織へ変えるGraph Engineering完全入門」で挙げられている
実践項目を、そのまま点検項目にしています。

| 部品 | 決めること | 点検が止めるもの |
|---|---|---|
| **ノード** | 1担当に任せられる大きさまで割る | 名前・仕事の中身が空 |
| **契約** | 入力・出力・失敗時の動作 | OUTPUT が0項目／失敗時の動作なし |
| **偽のエッジ** | 前の結果が本当に要るか | 依存を引いたまま未検査 |
| **検証者** | 作業者と別の文脈で反証を試みる | 検証ノードなし／自分自身を検証／観点が空 |
| **アンカー** | 何をもって正しいとするか | 1件も宣言していない |
| **人間ゲート** | 不可逆な行動の手前 | 不可逆ノードの手前にゲートがない |
| **上限** | 最大エージェント数・並列数 | 未設定／実行側の上限(同時16・総計1000)超え |

「偽のエッジ」がいちばん効きます。直列に並んでいる仕事の大半は、依存があるからではなく、
**人がその順番で書いたから**そうなっています。

## 1つの段には、いくつでも並べられます

調べる対象が違うものは、別々の「並列」にして同じ段に置きます。
同梱の **新商品の立ち上げ** ひな形がその形です。

```
 1段目 [同時に 8 本]      2段目     3段目      4段目 [同時に 4 本]
┌──────────────┐
│ 並列  競合の  │───┐
│ 料金    ×4    │   │
└──────────────┘   │   ┌──────┐  ┌──────┐  ┌──────────────┐
┌──────────────┐   │   │ 整理 │  │ 統合 │  │ 並列  出す物  │
│ 並列  顧客の  │───┼──▶│ 重複 │─▶│ 訴求 │─▶│ を書く   ×4   │─▶ 検証 ─▶ 統合
│ 不満    ×3    │   │   │ を畳 │  │ 決め │  └──────────────┘
└──────────────┘   │   └──────┘  └──────┘
┌──────────────┐   │
│ 単発  表現の  │───┘
│ リスク確認    │
└──────────────┘
```

部品を新しく置いたとき、**並列と単発は依存なし（＝1段目）から始まります。**
前の部品へ自動でつなぐと、記事が言うとおり「人が書いた順番」がそのまま偽のエッジになるからです。
整理・検証・統合・人間ゲートは、定義上その前の結果を食べるので、
まだ誰にも使われていない部品を自動で受け取ります。

**生成されるコードも、同じ段は本当に同時に走ります**（1つの `parallel` にまとめます）。
図が「同時に 8 本」と言っているのに順番に動く、ということは起きません。
段の合計が並列上限を超えたら点検が止めます。

## 1体が複数件返す

既定では **1体が1件**返します。これは調べものだと足りません。
「競合の料金を4本立てて調べる」と書いても、**集まる材料は4件**にしかならないからです。

並列の部品に **1体が複数件返す** があります。入れると、契約が「1件」から「件の配列」に変わり、
指示にこの3行が足されます。

> 見つかったものは1件ずつ items に入れて、まとめて返します。
> 1件しか返さないと、この段の材料はそれだけになります。
> **無理に数を作らず、確かなものだけを入れます。**

3行目は消さないでください。件数を目標にすると、AIは数を埋めにいきます。

一緒に **1体あたり何件くらい返る想定か**（`each`）を決めます。これは AI に渡す数ではなく、
**見積り・空回し・上限判定の目盛り**です。

| これが変わる | どう変わる |
|---|---|
| 表題欄の見積り | 4本 × 想定10件 = **40件**として数える |
| 上限の点検 | この数で上限に当たるかを判定する |
| 空回し | `--each 10` に渡した数だけ偽の返事を作る |
| 欠けの検出 | 「返った体の数」と「返った件数」を別々に数え、体が返ったのに中身が空なら落とす |

⚠ **空回しは `--each` に渡した数でしか答えません。** 実測前に想定だけで空回ししても、
それは自分が入れた数字が返ってきているだけです。次の「走らせる前の手順」を見てください。

## 検証は「何を確かめるか」で中身が入れ替わります

検証の部品には **何を確かめるか** があります。4つから選ぶと、
検証者に渡す問い5項目と、KEEP / DROP の言葉が**丸ごと入れ替わります**。

| 何を確かめるか | 使う段 |
|---|---|
| **事実として正しいか** | 調べた材料・数字・出典を確かめる |
| **決めた基準どおりか** | 指摘した箇所が直ったか、規約・チェック項目に沿っているか |
| **読み物として成立しているか** | 文章・体験の質。事実確認とは別の物差し |
| **手元で再現できるか** | 手順・コード・設定が実際に動くか |

「事実として正しいか」の検証者に「文章が読みやすいか」と聞いても答えは返りません。
**段ごとに物差しが違う**ので、選ばせています。

### 判定の基準は、別枠で手渡します

**検証者は「検証する相手」の出力しか読みません。** 依存の線を引いても中身は渡りません。
だから **判定の基準として渡すもの** という別の欄があります。

> 検証する相手＝**採点する答案** ／ 判定の基準＝**模範解答**

答案だけ渡して採点しろと言えば、検証者は自分の記憶で採点します。
「決めた基準どおりか」「再現できるか」を選んだのに基準が空だと、点検が止めます。

| 点検 | 止める理由 |
|---|---|
| `K-37` 基準を見る検証なのに基準が渡っていない | 何と照らすのかが検証者の手元にない |
| `K-38` 依存に入れても検証には渡らない | 依存＝順番待ちであって、中身は届かない |
| `K-39` 基準が検証する相手と同じ | 相手の出力は既に渡っている。基準として何も足していない |
| `K-40` 基準がこの検証より後ろにある | まだ結果が出ていないものは基準にできない |

`K-38` は、最初にこの設計盤を使った人が実際に詰まった場所です。
**依存に入れれば渡ると読むほうが自然**なので、機械の側が気づいて言うようにしました。

## 「直さない段」は、指示ではなく道具を取り上げて止めます

部品の詳細に **この仕事はファイルを書き換えますか** があります。
**書き換えない**と答えた段は、**書く道具を持たない担当**で走ります。

外れるのは `Edit` / `Write` / `NotebookEdit` / `Bash` / `PowerShell` / `Agent` の6つだけです。
**ブラウザ操作（MCP）も、読むことも、探すことも、今までどおりできます。**

| なぜこれも外すのか | |
|---|---|
| `Bash` | `printf > file` や `rm -f` で書けてしまう。**実測で、この2つは実際に使われました** |
| `Agent` | 別の担当を呼べば、その担当が書けてしまう |

⚠️ **＝コマンドの実行が要る段は「書き換える」を選んでください。**
半端に外すと「書けないことになっているのに書ける」状態になり、そのほうが危険です。

### なぜ指示では足りないのか

このひな形を実際に走らせて、こうなりました。

```
洗い出す（書かない宣言） … 1体が実装ファイルを 7回編集
テストを実施（書かない宣言）… 実装ファイルを 41回編集
落ちたものを直す（書いてよい）… 1文字も書かず「直すもの無し」
```

実施の担当が**テストしながら自分で直し、自分が直したものをテストして「51件中0件が失敗」と報告**しました。
次の段には直すものが残らず、検証者は「直すものが無いのは正しい」と合格を出しました。
**結果、実際に行われた413行の変更を、誰も検証しないまま通りました。**

検証は正しく働いていました。**検証する相手が入れ替わっていた**のです。
指示文に「直さないでください」と書いても止まらなかったので、道具の側を外しました。

**検証ノードは、答えに関係なく常に書けません。** 検証者が直せるなら、それは検証ではありません。

### プラグインを入れずに使うときは

この担当はプラグインが持っています。Artifact からスクリプトだけを落とした場合は見つからないので、
**書ける状態のまま続きます。ただし黙って落としません。** 走らせると出ます。

```
⚠ 「テストを実施する」を、ファイルを書けない担当で走らせようとしましたが見つかりませんでした。
   書ける状態のまま続けます。この段が成果物を書き換えても、機械には止められません。
```

⚠️ **入れた直後の同じセッションでも、同じことが起きます。**
担当が使えるのは**次のセッションから**です。入れてすぐ走らせると、上の警告が出て
書ける状態のまま進みます（実測で踏みました）。入れたらセッションを開き直してください。

### 整理には「中身の欠けた行を落とす」があります

体は返ったのに項目が空、は**返らなかったのと同じくらい静かに欠けます**。
入れておくと、契約の項目が1つでも空いている行を落とし、`整理: 中身の欠けた 3件を落としました` と件数を出します。

## あとから段を入れる・種類を変える

**「1段目の前にもう一段必要だった」は普通に起きます。** 段の見出しにある
**＋ この前に一段** から、**入れる部品の種類を選ぶ**とその段の手前に一段入ります
（単発／並列／整理／検証／統合／人間ゲート）。

- 新しい部品は、**その段が持っていた依存をそのまま引き継ぎます**
- その段の部品は、新しい部品を待つようになります（＝まるごと1つ下がる）
- **もとの依存は消しません。** 消すと整理ノードが素材を見失うからです

部品の詳細からも **＋ この部品の前に一段入れる** で、1つの部品の手前にだけ入れられます。
段まるごとではなく1本だけ分岐させたいときはこちらです。

### 入れた直後は、線が余分に引かれています

段の手前に入れると、**その段の全員に線が引かれます**。でも実際にその結果を必要とするのは
一部だけ、というのがほとんどです。

たとえば「新商品の立ち上げ」の1段目の前に *競合がどこにあるのか調べる* を入れると、
*顧客の不満* と *表現リスク* にも線が引かれます。この2つは競合が分からなくても始められるので、
**その2本は偽のエッジ**です。

だから入れた直後、線を引かれた側は**未検査**になり、点検が
`「顧客の不満を集める」の依存が偽のエッジか未検査です` と全部に出します。
機械が勝手に引いた線を、そのまま通さないためです。

外すのは、入れた部品の詳細にある **この結果を待つ仕事** から。外した仕事は1段目に戻り、
最初から走ります。

```
入れた直後                          余分な2本を外したあと
1段目 [競合がどこに]                1段目 [競合がどこに, 顧客の不満, 表現リスク] 同時5本
2段目 [競合の料金, 顧客の不満,      2段目 [競合の料金]                          同時4本
       表現リスク]      同時8本      3段目 [整理] …
3段目 [整理] …
      ↑ 2本が無駄に待っている        ↑ 待たなくていいものは待たない
```

**段は「開始条件」ではありません。** 依存の深さを表示しているだけで、
線が入っていない仕事は最初から走ります。

置いたあとで種類を変えたくなったら、部品の詳細の **種類** で移せます
（並列 → 単発 のように移すと、要らなくなった項目は落ちます）。

## 繰り返し（テスト→修正→再テスト）

同じ段を「合格するまで」回したいときは、**部品ではなく帯**を使います。
左の **繰り返し** で、どの段からどの段までを何周まで回すかを決めます。

```
                          ╭─ 繰り返す 最大5周 / 2周続けて新しい指摘が無ければ終了 ─╮
┌────────┐  ┌──────┐  │ ┌────────┐  ┌────────┐  ┌────────┐          │
│ 並列    │─▶│ 整理 │─▶│ │ 単発    │─▶│ 単発    │─▶│ 検証    │          │
│ 操作を  │  │      │  │ │ テスト  │  │ 落ちた  │  │ 直った  │          │
│ 洗い出す│  └──────┘  │ │ を実施  │  │ ものを  │  │ か判定  │          │
│ ×8      │            │ └────────┘  │ 直す    │  └────────┘          │
└────────┘            │              └────────┘   ↑合否はここが出す    │
                          ╰────────────────────────────────╯
```

**止まらなくなるのが一番怖いので、停止条件は必須です。** 揃うまで書き出せません。

| 点検 | 止める理由 |
|---|---|
| `K-25` 繰り返しの中に検証がない | 何をもって合格とするか決まらず、永久に回る |
| `K-26` 最大周回数が未設定 | 上限が無いと止まらない |
| `K-27` 空回りの判定回数が未設定 | 新しい指摘が出なくなっても回り続ける |
| `K-28` 人間ゲートをまたいでいる | 実行中に承認は挟めない |
| `K-36` 繰り返しの中の仕事が、直す対象を受け取っていない | 指摘だけが渡り、**直す現物が手元に無い**まま直すことになる |
| `K-41` 繰り返しの中から、繰り返しの外にある現物を直に読んでいる | 外にあるものは毎周おなじ（1周目のまま）。2周目以降、**最新の指摘と古い現物**を同時に渡される |

`K-41` は目で見つけるのが難しい種類です。図としては線が1本引いてあるだけで、
1周目は正しく動きます。**2周目から静かに積み上がらなくなる**ので、機械に見張らせています。

抜け方は3つです。**全部通った** / **指定した周だけ空回りした**（新しい指摘が出なくなった）/
**最大周回に達した**（この場合は「終わっていない」と明示して残します）。

繰り返しの中の部品は、**見積りに周回数が掛かります**。上の例は 24体（8+1+5×3）で、
上限を超えれば点検が止めます。

⚠️ **ブラウザ操作のテストを並列にしないでください。** ブラウザは1つしかないので、
複数のエージェントが奪い合って壊れます。記事の言う「独立しているように見えて
独立していない」隠れたエッジです。**洗い出しは並列、実施は直列**にします。
点検では捕まえられません（機械には「同じブラウザを使う」ことが見えない）。

同梱の **UI操作の不備を潰す** ひな形がこの形です。

## 知っておく制約

- **実行中に人間の入力は挟めません。** 承認が要る設計は、設計盤が**図面を2枚に割ります**
  （承認前 / 承認後）。1枚目が終わったら、人が承認して2枚目を起動します。
- 同時実行は最大16エージェント、1回の実行全体で最大1000エージェント。
- dynamic workflows は **Claude Code v2.1.154 以降**。Pro プランでは `/config` の
  「Dynamic workflows」を有効にしてください。
- **整理（Reduce）は LLM を呼びません。** 重複削除・件数確認は素のコードの方が安く速く確実です。
  生成されるスクリプトも、その部分はただの JavaScript です。
- 生成スクリプトを手で直すと、次の書き出しで上書きされます。**図面側を直してください。**

## 生成されるものの形

```javascript
export const meta = {
  name: 'article-build',
  description: '出典の付いた1万字の記事を、密度を落とさずに仕上げる',
  phases: [{ title: '調査' }, { title: '検証' }, { title: '統合' }],
}

// アンカー（AIの合意ではなく現実の証拠）:
//   - 一次情報（公式ドキュメント・原典）
//   - 実際に手元で再現できた結果

phase("調査")
const r_n1 = (await parallel(r_n1_items.map((angle) => () =>
  agent(`... 観点: ${angle}`, { schema: {...}, phase: "調査" })
))).filter(Boolean)

// 整理はLLMを呼びません。
const r_n2_missing = r_n2_expected - r_n2_returned
if (r_n2_status === "INCOMPLETE") log("⚠ 返らなかった仕事があります。…")

phase("検証")
// 検証者には作業者の会話履歴を渡しません。完成物と基準だけを渡します。
```

## 書き出したものを、AIを呼ばずに空回しする

```bash
graphflow-dryrun .claude/workflows/uiux-sweep.js
```

```
✅ uiux-sweep.js は最後まで走りました（1ms）

  呼ぶAIの数: 18 体
  繰り返し:   3 周（検証がずっと不合格を返す最悪の場合）
  節ごとの数:
    並列: 8 体 / 統合: 1 体 / 実行: 6 体 / 検証: 3 体
```

`agent()` は本物のAIを呼ばず、契約どおりの形をした偽の返事を返します。**課金は発生しません。**
分かるのは3つです。

- **最後まで走るか**（構文だけでなく、実行時に落ちないか）
- **AIを何体呼ぶことになるか**（走らせる前に費用の桁を掴む）
- **繰り返しが本当に止まるか** — 既定は「検証がずっと不合格を返す」最悪の場合で回します。
  `--pass` を付けると「全部合格」の前提でも回せます

- **AIが落ちたときに、落ちたと分かるか** — `--null 3` で「3体に1体が `null` を返す」状況を作れます

記事の言う「まず3件、5件、10件で試す」の前に、**0件で試す**ための道具です。

### 「1体が複数件返す」を使ったら、順番があります

空回しは **`--each` に渡した数でしか答えません。** 想定10件と書いて `--each 10` で空回しすれば、
当然10件返ってきます。それは**自分が入れた数字を見ているだけ**で、何も確かめていません。

```
① 空回し                       課金0。最後まで走るか・構造を見る
② 1回だけ本当に走らせる        1体が実際に何件返すかを測る  ← ここが要
③ 測った数で空回しし直す        --each <実測値>。上限に当たるか分かる
④ 本番
```

②を飛ばすと、①の見積りは**当たっているように見えて根拠がありません**。
上限に当たるかどうかは、この実測値でしか判定できません。

```bash
graphflow-dryrun .claude/workflows/foo.js --each 10
```

## AIが1体落ちても、黙って進みません

公式仕様で **`agent()` は、途中で止めたときや回復不能なAPIエラーのとき `null` を返します**
（<https://code.claude.com/docs/en/workflows>）。素直に書くと `.filter(Boolean)` で落ちた分を捨てるので、
**落ちたこと自体が消えます**。100体で調べて97体しか返らなくても、報告書は普通に出てきます。

書き出すスクリプトは、`null` を全部つかまえます。

| 落ちた場所 | 起きること |
|---|---|
| 並列の1本 | `⚠ 1件が返っていません` と件数を出す（整理ノードの件数確認と二重で見る） |
| 検証者 | その項目を**捨てずに `UNVERIFIED` にする**。KEEP でも DROP でもなく「確認できていない」として残る |
| 単発・統合 | `⚠ 「◯◯」が結果を返しませんでした` を出し、戻り値の `status` を `INCOMPLETE` にする |
| 繰り返しの合否 | **未確認が残っている限り「全部通りました」と言いません**（`未合格 0 かつ 未確認 0` で初めて抜けます） |

いちばん危ないのは検証者が落ちた場合です。捨ててしまうと、**確認できなかったものが
「検証を通った」側に混ざらないまま静かに消え**、繰り返しは「全部通った」と判断して止まります。
Anthropic 自身も、同梱の `/deep-research` で **v2.1.196** に同じ直し方をしています
――「検証者が確認できなかった主張は、否定されたのではなく未確認として報告する」。

確かめ方:

```
graphflow-dryrun .claude/workflows/foo.js --pass --null 3 --log
```
